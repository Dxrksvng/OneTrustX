## Slide 1 — Problem / Pain Point (60 วินาที)

**ปัญหาเดียว: กระเป๋าขาออกไปไม่ทันเที่ยวบิน (delayed baggage)**

- บริบทอุตสาหกรรมล่าสุด: SITA Baggage IT Insights 2026 รายงานว่าในปี 2025 มีกระเป๋า *mishandled* ราว 24 ล้านใบ และประเมินต้นทุนอุตสาหกรรมราว 6.3 พันล้านดอลลาร์ต่อปี
  - ถ้าต้องเชื่อมกับตัวเลขในวัน kick-off: ปี 2024 คือ 33.4 ล้านใบ / ราว 5 พันล้านดอลลาร์ แล้วบอกชัดว่าเป็นคนละปี
  - พูดว่า "mishandled (ล่าช้า/เสียหาย/ส่งผิด)" ไม่ใช่ "หาย"
- SKY บอกเองว่าปัญหาเกิดที่ **รอยต่อ** ตอนเปลี่ยนมือระหว่างฝ่าย (check-in, loading, transfer, arrival)
- ช่องว่าง: แต่ละฝ่ายเห็นแค่ขั้นของตัวเอง เมื่อกระเป๋าเริ่มค้าง ไม่มีใครเห็นภาพรวมว่า **ค้างที่ขั้นไหน เพราะอะไร** จนกระทั่งเที่ยวบินได้รับผลแล้ว

ภาพประกอบ: ใช้เส้น Hold Baggage Process จาก flow ที่ SKY แสดงในวัน kick-off

```
Check-in -> Screening & Handling -> Loading -> Aircraft Turnaround -> Unloading -> Baggage Claim
```

สาเหตุของความล่าช้าแยกตามขั้น (สมมติฐานของทีม ต้องยืนยันกับ mentor ก่อนขึ้น slide):

| ขั้น | สาเหตุที่เป็นไปได้ |
|---|---|
| Check-in | ผู้โดยสารมากระจุกตัว, bag drop ปิดช้า |
| Screening & Handling | กระเป๋าถูกส่งตรวจซ้ำ, สายพาน/เครื่องคัดแยกขัดข้อง |
| Loading | พนักงานไม่พอ, รถลาก/cart/ULD ไม่พอ, เปลี่ยน gate กะทันหัน |
| Transfer | เครื่องขาเข้ามาช้า ทำให้เวลาต่อเครื่องสั้นเกินไป |
| Unloading / Claim | พนักงานขนถ่ายไม่พอ, จัดสายพานรับกระเป๋าช้า |

เหตุการณ์อ้างอิง (ถ้าจะใช้เปิดเรื่อง): น้ำท่วม กทม. ปลาย ก.ย. 2026 ที่พนักงานภาคพื้นมาทำงานไม่ได้และมีกระเป๋าค้าง
**ต้องเปิดลิงก์ใน `data/scenarios/scenario_library.json` ตรวจตัวเลขและวันที่ก่อนใช้** และต้องบอกว่าเป็นเหตุการณ์อ้างอิง ไม่ใช่ผลของระบบเรา

## Slide 2 — Target User / Stakeholder (30 วินาที)

- **ผู้ใช้หลัก:** Baggage / Ground Operations Controller (คนที่ต้องตัดสินใจว่าจะย้ายคนและอุปกรณ์ไปช่วยตรงไหน)
- **ผู้ใช้รอง:** Airline OCC (ตัดสินใจรอ/ไม่รอกระเป๋า), Airport Operations
- **ผู้ได้ประโยชน์:** ผู้โดยสาร ตรงกับ pain ที่อาจารย์ CATC ยกตัวอย่าง "กระเป๋าอยู่ไหน"

## Slide 3 — Proposed Solution (60 วินาที)

**One TrustX — Baggage Delay Control View**: จอเดียวที่แสดงสถานะงานกระเป๋าทีละขั้น โดยยังคง trust/event layer, common operational state, scenario, recommendation, human approval และ audit เดิมไว้ทั้งหมด

สถานะปกติ (มองแล้วรู้ทันทีว่าไม่มีปัญหา):

```
Check-in   Screening   Loading   Transfer   Unloading   Claim
   OK          OK         OK         OK          OK        OK
```

เมื่อมีปัญหา (รู้ทันทีว่าเกิดที่ส่วนไหน):

```
Check-in   Screening   Loading   Transfer   Unloading   Claim
   OK          OK       DELAY       RISK         OK        OK
                          |
   สาเหตุ:   พนักงานโหลดต่ำกว่าแผน, รถลากไม่พอ
   กระทบ:    เที่ยวบินที่กำลังจะออกในช่วงถัดไป และกระเป๋าต่อเครื่อง
   ควรทำ:    ย้ายทีมโหลดไปเที่ยวบินที่ใกล้ออกที่สุดก่อน
```

หลักการออกแบบ: ไม่โชว์ทุก KPI โชว์แค่ 3 คำตอบ คือ ปกติไหม / ติดที่ไหนเพราะอะไร / ควรทำอะไรก่อน
คนตัดสินใจสุดท้ายคือเจ้าหน้าที่ ระบบแค่แนะนำ

## Slide 4 — How It Works / Solution Journey (75 วินาที)

```
ข้อมูลจากแต่ละฝ่าย -> ตรวจความสอดคล้อง -> สถานะรายขั้น -> หาคอขวดและสาเหตุ -> ประเมินผลกระทบ -> แนะนำลำดับการแก้ -> เจ้าหน้าที่ตัดสินใจ
```

**ใช้ข้อมูลอะไร จากใคร เพื่อโชว์อะไร**

| ข้อมูล | มาจากฝ่ายไหน | ใช้ตอบคำถาม |
|---|---|---|
| จุดสแกนกระเป๋ารายขั้น (BSM, check-in/loading/transfer/arrival) | BRS ของ SKY | กระเป๋าไหลผ่านแต่ละขั้นทันเวลาไหม |
| ETD/ETA, gate, สถานะเที่ยวบิน | AODB | เส้นตายของแต่ละเที่ยวบิน, เที่ยวบินไหนได้รับผล |
| จำนวนพนักงาน, รถลาก, cart/ULD | Ground handler | คอขวดเกิดจากคนหรืออุปกรณ์ |
| สถานะสายพาน/เครื่องคัดแยก | ผู้ดูแล BHS | คอขวดเกิดจากระบบสายพานไหม |
| เที่ยวบินต่อเครื่องและเวลาต่อเครื่อง | สายการบิน | กระเป๋าใบไหนเสี่ยงที่สุด ควรทำก่อน |
| ฝน/น้ำท่วม/เหตุภายนอก | กรมอุตุฯ, ประกาศทางการ | ปัจจัยเสี่ยงล่วงหน้า |

ไม่ใช้ชื่อหรือเลขหนังสือเดินทางของผู้โดยสาร

## Slide 5 — Value & Differentiation (45 วินาที)

| ระบบที่ SKY มีแล้ว | ตอบคำถาม | One TrustX เพิ่มอะไร |
|---|---|---|
| BRS | กระเป๋าใบนี้อยู่ที่ไหน ผ่านจุดไหนแล้ว | ภาพรวมรายขั้น + สาเหตุ โดยรวมข้อมูลคนและอุปกรณ์ที่ BRS ไม่มี |
| AODB | เที่ยวบินออก/ถึงกี่โมง gate ไหน | ใช้เป็นเส้นตายในการจัดลำดับ |
| A-CDM | ทุกฝ่ายทำงานตาม milestone ของเที่ยวบิน | ไม่สร้าง A-CDM ใหม่ เจาะเฉพาะงานกระเป๋า |
| Smart Flows | ผู้โดยสารมาถึงเมื่อไหร่ หนาแน่นตรงไหน | ใช้เป็นสัญญาณล่วงหน้าของปริมาณกระเป๋าที่ check-in (ระยะถัดไป) |

ประโยคหลัก: **"BRS ตามกระเป๋า One TrustX ดูแลความล่าช้ารอบกระเป๋า"**
อย่าพูดว่า BRS ทำไม่ได้ พูดว่าเราต่อยอดจากข้อมูล BRS/AODB ที่มีอยู่

## Slide 6 — Feasibility (40 วินาที)

- ไม่ต้องติดเซนเซอร์ใหม่ทั้งสนามบิน: BRS มีใช้ที่ BKK, DMK, HKT แล้ว และ SKY มี AODB อยู่แล้ว
- ข้อมูลที่ต้องขอเพิ่มมีแค่ฝั่ง ground handler (คน/อุปกรณ์) และสถานะ BHS
- ทีมมี engine ตรวจความสอดคล้องของ event และชุด scenario จำลองอยู่แล้ว (พูดได้ว่า "มีโครงต้นแบบสำหรับทดลองแนวคิด" ห้ามอ้างเป็นผลลัพธ์)
- ความเสี่ยงที่ต้องบอกตรง ๆ: การเข้าถึงข้อมูลจริงของ ground handler และการยืนยันสาเหตุรายขั้นกับผู้เชี่ยวชาญ

| ตัวชี้วัด | วัดอย่างไร |

| เวลาที่ใช้กว่าจะรู้ว่าคอขวดอยู่ขั้นไหน | เทียบการทำงานแบบเดิมกับแบบมีจอ บน scenario เดียวกัน |
| เวลาประสานงานระหว่างฝ่าย | จับเวลาตั้งแต่เกิดเหตุจนมีการตัดสินใจ |
| จำนวนกระเป๋าที่เสี่ยงพลาดเที่ยวบิน/ต่อเครื่อง | นับจาก scenario จำลอง แล้วยืนยันกับผู้เชี่ยวชาญ |

## เตรียม Q&A (7 นาที)

- **ต่างจาก BRS ยังไง:** BRS ดูรายใบที่จุดเปลี่ยนมือ เราดูรายขั้นและรวมข้อมูลคน/อุปกรณ์เพื่อบอกสาเหตุ
- **ต่างจาก A-CDM ยังไง:** A-CDM คุม milestone ของเที่ยวบินทั้งหมด เราเจาะงานกระเป๋าเรื่องเดียว
- **ซ้ำกับทีมที่ทำ flight delay ไหม:** เขาเริ่มจากเที่ยวบิน เราเริ่มจากกระเป๋า และกระเป๋าล่าช้าเป็นหนึ่งในสาเหตุของ delay
- **ข้อมูล ground handler จะได้มาอย่างไร:** ยังไม่มี รอบ prototype ใช้ข้อมูลจำลองที่ติดป้ายชัดเจน
- **ตัวเลขผลลัพธ์มีไหม:** ยังไม่มีผลจากข้อมูลจริง มีแค่การจำลองเพื่อทดสอบแนวคิด
