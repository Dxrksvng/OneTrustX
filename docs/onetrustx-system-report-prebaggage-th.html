One TrustX: รายงานระบบฉบับก่อนกระเป๋า

อ้างอิง commit 386d911 (Add One TrustX prototype, provenance, and workflow diagrams) · ระบบเวอร์ชันนี้ยังไม่มีโมดูลกระเป๋า · เอกสารนี้รวบรวมจาก docs/evaluation.md และ docs/project-handoff-th.md ในคอมมิตดังกล่าว
ตัวเลขผลลัพธ์ทั้งหมดในเอกสารนี้เป็นค่า SYNTHETIC ที่ถูกกำหนดไว้ในโค้ด ไม่ใช่ผลการวัดจากสนามบินจริง ค่าสัมประสิทธิ์ที่ใช้คูณค่าพื้นฐานอยู่ใน scripts/experiments/generate_validation_pack.py เช่น 0.62, 0.44, 0.39 และ 0.22 ตัวเลขการลดลงที่แสดงด้านล่างจึงเป็นผลของค่าเหล่านี้โดยตรง เอกสารต้นฉบับบางจุดเรียกว่า "measured" ซึ่งไม่ตรงกับโค้ด

1. ระบบนี้คืออะไร

เวอร์ชันนี้เป็น decision-support prototype สำหรับจำลองสถานการณ์ผู้โดยสารที่สนามบิน และเปรียบเทียบมาตรการ เช่น เปิดเลนสำรอง redirect ผู้โดยสาร หรือใช้มาตรการผสม ก่อนให้ผู้ปฏิบัติงานตัดสินใจ

ระบบไม่ใช่ระบบควบคุมสนามบิน และไม่ควรอ้างว่าตัวเลขคิวเป็นข้อมูลจริงของสุวรรณภูมิ ลำดับการทำงานหลักคือ:

Observe → Predict → Simulate → Compare → Human decision → Measure

2. สิ่งที่ระบบทำในเดโม

  1. แสดงสถานการณ์ปัจจุบันและ forecast ที่ +15, +30, +60 นาที
  2. จำลองคิวของ Security A/B ด้วยข้อมูลชุดเดียวกัน
  3. เปรียบเทียบ No Action, เปิดเลน, redirect และมาตรการผสม
  4. ตรวจข้อจำกัด เช่น จำนวนเลน, staff และ redirect cap
  5. ให้ operator Accept, Reject หรือ Override พร้อมเหตุผล
  6. บันทึก decision และผลลัพธ์จำลองลง audit trail
  7. จำลอง gate change และคำนวณ accessible route กับ Safe Time ใหม่

3. ป้ายกำกับข้อมูล

ป้ายความหมาย
REAL_PUBLICข้อมูลสาธารณะจริง ใช้เป็น context หรือ benchmark
SYNTHETICข้อมูล fixture ที่สร้างขึ้นสำหรับเดโม
ASSUMPTIONค่าที่สมมติ เช่น service rate และ topology
DERIVEDค่าที่คำนวณจากข้อมูลต้นทาง
SIMULATEDผลจาก engine เช่น queue, forecast และ recommendation

ข้อมูล operational ในเดโมเป็น SYNTHETIC และ SIMULATED เป็นหลัก ไม่มี passenger telemetry จริงของ BKK และไม่มีการสั่งงานอุปกรณ์สนามบิน

4. สถาปัตยกรรม

React/TypeScript frontend
        ↓ JSON + demo session
FastAPI API layer
        ↓
Deterministic simulation engine
        ↓
SQLAlchemy → SQLite (local) / PostgreSQL (Compose)

การคำนวณคิวใช้สูตรหลัก:

queue_next = max(0, queue_current + arrivals - lanes × service_rate)

Recommendation ใช้ weighted score ที่เปิดเผย และตรวจ resource constraints ไม่ได้สร้างตัวเลขด้วย LLM

7. Benchmark จากข้อมูลจริงสาธารณะ

ชุดข้อมูลจริงที่ใช้คือ CBP terminal/hour จำนวน 12,186 รายการจาก JFK, LAX และ SFO ช่วงมกราคม–มีนาคม 2025 โดยมี 12,178 รายการที่มีจำนวนเคาน์เตอร์ที่เปิดเป็นบวกและเข้าสู่ benchmark มกราคมใช้ train, กุมภาพันธ์ใช้ validate และมีนาคมใช้ test ไม่สุ่มลำดับ ผลอยู่ที่ data/cache/queue-benchmark.json

ชุดนี้เป็นข้อมูลของสหรัฐฯ ใช้เป็นบริบทและ benchmark ไม่ใช่ข้อมูลของ BKK

8. One TrustX validation pack (SYNTHETIC)

ชุด validation มี 8 สถานการณ์ สถานการณ์ละ 100 seeds และ 4 เงื่อนไข รวม 3,200 episodes ทุกเงื่อนไขใช้ scenario และ seed เดียวกัน ใช้ median เป็นค่าหลัก และ P25/P75 แสดงความแปรผัน

สถานการณ์: normal turnaround, baggage bottleneck, gate conflict, weather-affected, multi-factor disruption, data conflict, missing/late data และ scale test

ข้อควรรู้ก่อนอ้างตัวเลข:

  • การลด 61%, 78% และ 74% มาจากการคูณ baseline ด้วยสัมประสิทธิ์ที่กำหนดไว้ล่วงหน้า ค่า 85.7 และ 100 เป็นค่าคงที่ในโค้ด ไม่ได้คำนวณจากการตรวจข้อมูล
  • Delay risk proxy 0.50 เป็นค่าที่กำหนดไว้ ไม่ใช่โอกาสที่เที่ยวบินจะล่าช้าจริง
  • ไม่ควรเรียก recommendation success ว่า AI accuracy เพราะชุดนี้ไม่มีผลลัพธ์จริงที่ติดป้ายเป็นอิสระมากพอ
  • ต้นฉบับบางจุดเขียนว่า "measured" ซึ่งไม่ตรงกับโค้ด ควรใช้คำว่า "ค่าที่กำหนดในตัวสร้างข้อมูลสังเคราะห์"

ไฟล์ที่เกี่ยวข้อง: data/cache/onetrustx-validation-runs.csv, data/cache/onetrustx-validation-summary.csv และ data/cache/onetrustx-validation-manifest.json ข้อกำหนดข้อมูล telemetry จริงอยู่ใน docs/validation-data-contract.md

9. ข้อจำกัดของระบบ

  • ไม่มี aggregate checkpoint telemetry จากสนามบินจริง
  • ยังไม่มีการ calibrate โมเดลกับข้อมูลสนามบิน
  • ยังไม่มี temporal validation บนข้อมูลจริง
  • ยังไม่มีการตรวจความปลอดภัยและ pilot ที่มนุษย์อนุมัติ

10. สิ่งที่ควรพูดและไม่ควรพูด

ควรพูด: ระบบใช้ข้อมูลสาธารณะเป็นบริบท และใช้สถานการณ์สังเคราะห์ที่กำหนดได้ เพื่อสาธิตการเปรียบเทียบมาตรการจัดการคิวอย่างโปร่งใสและตรวจย้อนได้

  • ไม่ควรพูดว่าโมเดลทำนายคิวสุวรรณภูมิจากข้อมูลจริงได้แล้ว
  • ไม่ควรพูดว่าลดเวลารอได้ตามตัวเลขในเดโม
  • ไม่ควรพูดว่าผ่านการ validate กับสนามบินแล้ว
  • ไม่ควรพูดว่าใช้ข้อมูลผู้โดยสารจริงของ BKK

11. ความเชื่อถือได้ของระบบ (คำตอบสั้น)

เชื่อถือได้ในฐานะ prototype ที่แสดงกลไกการจำลอง การเปรียบเทียบทางเลือก ข้อจำกัดทรัพยากร และการตรวจสอบย้อนหลังได้แบบทำซ้ำได้ แต่ยังไม่ควรใช้ตัวเลขเป็นผลปฏิบัติการจริง จนกว่าจะมี telemetry จากสนามบิน การ calibrate การทดสอบตามเวลา การตรวจความปลอดภัย และ pilot ที่มนุษย์อนุมัติ
